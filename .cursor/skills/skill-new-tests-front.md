# Создание автотестов фронтенда

Универсальный скилл. Не подставляй факты и термины другого проекта. Не привязывай текст скилла к домену репозитория.

Роль: тестировщик UI. Цель запуска: закрыть пробелы автотестами по канону. Не цель: прогон, фикс продукта, лекции о теории тестирования.

Скилл **не** запускает `skill-use-tests-front` и **не** выполняет тесты (в т.ч. «на всякий случай» и `--collect-only` как замену прогону). Прогон — отдельная `/use-tests`.

---

## Редирект (сразу)

| Запрос | Действие |
| --- | --- |
| Только прогон / баги / «исправь падения» | Останови этот скилл. Напиши, что нужна `/use-tests`. |
| Нет ни требований, ни явного эталона в чате / `@` | Не выдумывай. Спроси с рекомендацией. |
| Post-MVP / «Вне MVP» без явного расширения | Не пиши тесты «для полноты». |

---

## SOP (порядок фиксирован)

Пустой `tests/` и отсутствие раннера — **не петля и не стоп**. Это старт с умолчаниями (§2, §4).

### 0. Режим (один)

| Режим | Когда | Шаги |
| --- | --- | --- |
| **дополнение** | «напиши тесты», `/new-tests`, указаны фичи / ID | §1 → §8 |
| **инвентаризация** | «какие тесты есть / чего не хватает», без «напиши» | §1–§3, затем чат как в примечании ниже. Файлы **не** создавай |
| **устаревшие** | канон сменился, ожидания в тестах ложные | §1–§2, правь эталоны по §5, затем §6–§8. Новые сценарии не плоди, если не режим дополнение |

Инвентаризация после §3: в чат только пробелы (ID + слой + состояние UI). `/use-tests` предлагай, только если файлы тестов уже есть.

Если в **дополнении** нашлись и ложные эталоны, и пробелы: сначала поправь ложные assert (§5), затем допиши пробелы. Не бросай дополнение, переключившись только на «устаревшие».

### 1. Канон ожиданий

Читай **узко**. Если в `$1` / `@` есть ID или экран — только они и связанные `Axxxx`. Иначе — Must UI текущего MVP. Архив — только по `@`. Память агента — только если просили учесть.

Приоритет при конфликте: запрос хода → `Axxxx` → согласованные ФТ/НФТ/US AC/UC → глоссарий/словарь → ТЗ в `documentation/` → код UI (что можно вызвать, не что «должно быть»).

Не тестируй поведение вне источников.

### 2. Инвентарь

Ищи `tests/`, `*.test.*`, `*.spec.*`, конфиг раннера, `tests/coverage.md`.

**Тестов нет (ноль файлов):** не ищи «стиль проекта» дальше. Умолчания: папка `tests/`, имена `test_should_<поведение>_when_<условие>`, карта `tests/coverage.md` (в инвентаризации карту не создавай). Переходи к §3.

**Тесты есть:** копируй их раннер и структуру. Дубли не добавляй. Эталон противоречит канону — поправь этот assert (как в режиме **устаревшие**). Если пользователь просил **дополнение**, после правок эталонов продолжай пробелы; не заканчивай запуск только сменой режима.

### 3. Пробелы (внутренний чек-лист)

Для каждого требования **в scope** отметь слои, которые **есть в источниках** (нет в источнике — нет теста):

| Слой | Смысл |
| --- | --- |
| `happy` | успешный пользовательский путь |
| `edge` | границы из канона (пусто, лимит, один/много) |
| `negative` | отказ, ошибка, отмена, невалидный ввод из ФТ/UC/AC |

Дополнительно к слою укажи **состояние UI**, если канон его описывает: `empty` / `loading` (прогресс, спиннер, disabled на время) / `error` / `disabled` / `success` / `dialog`. Это колонка карты, не четвёртый слой и не повод выдумать loading «как в SPA».

Приоритет записи: Must и критичные AC → Should. Не три теста на каждый метод кода.

Чек-лист внутренний, пользователя не жди. В чат — один раз: §8 (дополнение / устаревшие) или сразу после §3 (инвентаризация).

### 4. Поверхность и раннер

Определи поверхность по `src/` (не по желанию):

| Поверхность | Признаки | Тесты |
| --- | --- | --- |
| **web** | DOM, React/Vue/Svelte/HTML, Jest/Vitest/Playwright | Testing Library / принятый в репо раннер |
| **desktop** | tk/customtkinter/Qt/Wx и т.п. | Обработчики, состояние, чистые функции; без `mainloop` и живого окна |

Раннер: если есть — только он. Если нет — пиши файлы в стиле **pytest** (Python) или JS-раннера, который уже намекает `src/` (Vitest/Jest). Зависимость в `requirements.txt` / `package.json` **в этом запуске не добавляй**; в §8 напиши, что поставить, и предложи `/use-tests`. Набор не гоняй и не спрашивай разрешения писать сами файлы тестов.

Тест обязан завершаться в терминале. Не открывай GUI и не требуй ручного ввода. E2E с дисплеем — только если такой слой уже есть в репозитории **и** пользователь его явно просил.

Макет без логики: тестируй то, что в коде уже есть (подписи, начальные disabled). Не пиши полный предметный пайплайн, который нечем выполнить. Красный тест из‑за нереализованного правила допустим — пометь в §8. Логику продукта не дописывай.

### 5. Запись тестов

Артефакты (не инвентаризация): `tests/`, `tests/coverage.md`, фикстуры рядом (`tests/fixtures/`, `conftest`). Не `test-data/` без прямого задания.

**Имя:** `test_should_<поведение>_when_<условие>` (латиница). В docstring: ID (`FT-012`, `US-001`, `Axxxx`) + слой.

**Один тест — один исход.** Assert проверяет наблюдаемое: текст, доступность, значение поля, факт вызова границы. У assert — одна фраза, какую бизнес-проверку он делает.

**Селекторы (web):** `getByTestId` / `getByRole` / `getByLabelText`. `data-testid` (или канон репо) предпочтительнее CSS-класса и хрупкого текста. **Исключение на продукт:** на web можно добавить только `data-testid` (или уже принятый test-id), без смены поведения и вёрстки. Логику, стили, обработчики не трогай. На **desktop** test-id не выдумывай: имена виджетов и подписи из канона / существующего кода.

**Асинхронность:** никаких `sleep` / `waitForTimeout(N)`. Жди условие: `findBy*`, `waitFor`, polling с таймаутом, fake timers раннера — если в каноне есть задержка/прогресс. После действий — assert по состоянию, не по «прошло 300 мс».

**Сеть и внешние системы:** живые HTTP, облако и локальную модель в тесте не вызывай. Если сценарий бьёт во внешнюю границу — мокай её (fetch/XHR/клиент API/адаптер модели). Если сценарий только про поля/кнопки экрана — мок сети не обязателен. Правила экрана из канона (блокировки, склейка, нарезка, если они в ФТ) тестируй вживую, не мокай.

**Файлы/диск:** если предмет требования — запись файла, тестируй с временным каталогом и teardown. Иначе диск мокай или не трогай.

**Изоляция:** тесты независимы от порядка. Web: размонтирование / `cleanup` Testing Library после теста (DOM не протекает). Desktop: уничтожить виджеты/сбросить фикстуру. Временные файлы и cwd — teardown. Общие фикстуры — в `conftest` (или канон репо).

Без секретов и ПДн. Не ослабляй зелёный релевантный тест ради стиля.

В `.md` запрещён fence с языком `text`.

### 6. Карта покрытия

В режимах дополнение / устаревшие обнови `tests/coverage.md`:

| Тест | Файл | Требования | Слой | Состояние UI | Примечание |
| --- | --- | --- | --- | --- | --- |

Слой: `happy` / `edge` / `negative`. Состояние UI: `empty` / `loading` / `error` / `disabled` / `success` / `dialog` / `—`. Строки = реальные тесты.

### 7. Гейт (это и есть «тест качественный»)

Стоп, пока не выполнено всё:

- [ ] Эталон из канона §1, не из «так обычно во фронте».
- [ ] Нет дубля существующего теста; устаревшие эталоны поправлены или не добавлялись поверх.
- [ ] Имя `test_should_*_when_*`, есть ID и слой.
- [ ] Один исход; assert на наблюдаемое поведение.
- [ ] Селекторы по §5, **если поверхность web**; на desktop — виджеты/состояние по §5, не `data-testid`.
- [ ] Нет `sleep`; async ждёт условие.
- [ ] Если тест бьёт во внешнюю границу — она замокана; UI-правила экрана живые; после теста нет утечки DOM / виджетов / временных файлов (что создавал — то почистил).
- [ ] Живое окно не открывается.
- [ ] В продукт не вносилось ничего, кроме разрешённого `data-testid` на web.
- [ ] `tests/coverage.md` синхронен (не для инвентаризации).
- [ ] Не использован `test-data/` без задания.

### 8. Чат

Кратко, без кода тестов:

1. Режим, пути, число тестов.
2. Чек-лист: ID + слой + состояние UI.
3. Что не покрыто и почему (нет в каноне / вне MVP / нет раннера — зависимость не ставил).
4. Предложение отдельной `/use-tests`, **если в этом запуске есть или появились файлы тестов**. Не запускай её. Если раннера в проекте ещё нет — одна строка, какую зависимость поставить.

Не коммить. В память не пиши без просьбы.

## Запрещено

- Выдумывать правила UI, пороги, loading/error «как в любом SPA».
- Гонять набор или выполнять `skill-use-tests-front`.
- Менять логику продукта, чтобы тест «уже был зелёный».
- Мокать внутреннюю логику UI; бить в живой API/модель.
- Три слоя на каждую функцию кода; тесты вне scope §1 (при пустом `$1` — только Must UI MVP, не Could и не «Вне MVP»).
- Ручной чек-лист «кликни в окне» вместо автотеста.
