# Контроль качества DDD-модели

Прочитай и выполни `.cursor/skills/skill-quality-control-ddd.md` целиком. Команда `/qc-ddd` запускает этот скилл.

Скилл написания (`skill-ddd`) — только канон формы: не выполняй его алгоритмы и не вызывай `/ddd` «заодно».

## Ввод

`$1` и дальнейший текст — уточнение: путь к модели, глоссарию, ФТ, US, UC; куда сохранить отчёт.

Если текста нет — проверь `requirements/domain-model.md`. Отчёт пиши в `reports/domain-model-review.md`.

## Какой режим

Смотри на ввод, отдельную подкоманду выбирать не нужно.

- **Отчёт без правок** (самостоятельный режим) — нет ответов по §4 и нет фраз вроде «примени §4», «внеси», «согласен» по пунктам QC. Типично: пустой `/qc-ddd`, «проверь модель», «аудит DDD». Файл модели не меняй.
- **Перенос §4** — в чате или в отчёте уже есть «примени §4», «согласен», ответы по дополнениям, либо явно сказано обработать §4. Внеси правки в `domain-model.md`; повторный `/qc-ddd` по тем же правкам не предлагай.

Если в одном сообщении и «проверь», и «примени §4» — сначала перенос §4, новый полный аудит не начинай, пока пользователь его явно не попросил.

Заключительный этап `/ddd` — режим «после /ddd» в том же скилле; отдельный `/qc-ddd` для этого не нужен.

## После выполнения

Кратко: путь отчёта, есть ли критические C-находки, перенесён ли §4 в модель. Не дублируй таблицы отчёта в чат.

- Аудит без согласия: файл модели не меняй.
- В запросе есть согласие на §4: внеси по режиму «Перенос §4». Не предлагай и не запускай повторный `/qc-ddd` по тем же правкам.
