## Режимы `/qc-ft-nft` и `/qc-us-uc`

Отдельной подкоманды нет: режим выбирается по содержимому запроса.

**Отчёт без правок** (шаги 1–2 скилла) — когда ещё нечего вносить. Типично: пустой `/qc-ft-nft` или `/qc-us-uc`, «проверь ФТ/НФТ», «проверь US/UC», «аудит». Агент пишет отчёт, колонку «ответ» оставляет пустой, файлы требований / US / UC не меняет.

**Перенос ответов** (шаг 3 скилла) — когда ответы уже есть: в чате («согласен», «да», текст по пунктам), в колонке «ответ» отчёта или явная фраза «обработай ответы» / «внеси». Агент правит файлы, записывает закрытые пары в `requirements/answers-project.md` (`Axxxx`), повторный QC по тем же правкам не предлагает.

Практический цикл:

1. `/qc-ft-nft` или `/qc-us-uc` — получить отчёт.
2. Ответить в чате или в таблице отчёта.
3. Снова та же QC-команда и в том же сообщении ответы либо «обработай ответы из отчёта».

Для `/qc-us-uc`: «проверь и исправь» в одном запросе — сначала отчёт, сразу правятся только пункты типа «Исправление» (данных в источниках уже достаточно). Строки-вопросы без ответа догадкой не закрываются.

Если в одном сообщении и «проверь», и ответы — сначала перенос ответов, новый полный аудит сам не начинается. Новый QC — только по явной просьбе или если появились новые требования / истории / сценарии сверх того отчёта.

## Режимы `/new-tests`

Отдельной подкоманды нет: режим выбирается по содержимому запроса.

**Дополнение** — «напиши тесты». Агент читает требования и старые тесты, добавляет только пробелы в `tests/`, обновляет `tests/coverage.md`. Продуктовый код не меняет.

**Инвентаризация** — «какие тесты есть», «чего не хватает». Код тестов не пишет, пока не попросили добавить.

**Обновление устаревших** — канон требований сменился. Правит только ложные ожидания в уже существующих тестах.

После дополнения предлагает `/use-tests` отдельной командой и **не** запускает её в том же прогоне (даже если написали «и прогони»). Если просят только прогон / баги — это `/use-tests`, не `/new-tests`.

## Режимы `/use-tests`

Отдельной подкоманды нет: режим выбирается по содержимому запроса.

**Прогон** — типичный `/use-tests`. Агент гоняет все тесты, пишет `reports/test-run.md` с очередью `BUG-…` (эталон для агента-разработчика) и краткое резюме в чат. Код не меняет. При падениях продукта предлагает исправить по отчёту.

**Прогон и исправление** — в запросе есть «исправь» / «почини». Сначала отчёт, затем правки только `product_bug`. Лимит: 2 попытки на баг, 4 полных прогона набора; полный набор в конце, не после каждого бага. Нет прогресса — `стоп-лимит`. Тесты под баг не подгоняет. Watch-раннер не использует.

**Повтор после фикса** — «перепрогони». Обновляет отчёт и статусы очереди.

Нет тестов — предлагает `/new-tests`, набор не выдумывает.

## Режимы `/ui-prototyping`

Отдельной подкоманды нет: режим выбирается по содержимому запроса. Это одна команда, не три.

**Создание** — «сделай макет». Агент пишет **окно приложения** (не браузер): красивый вид, подписи, нажимающиеся кнопки, без функционала. В конце: путь к коду, заголовок окна, как открыть launcher в проводнике.

**Правка** — макет есть. Меняет вид и удобство, напоминает перезапустить тем же launcher. README с нуля не пишет, если способ запуска не сменился.

**Только запуск** — «не вижу окно». Код не трогает. В чате: launcher в проводнике и заголовок окна (не URL браузера).
